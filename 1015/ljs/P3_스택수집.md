# P3(.60) 핵심 스레드 스택 수집 — 재시작 전에 실행

**재시작, `wsl --shutdown`, `wsl --terminate` 금지.**
WSL 안에서 `ip`, `ifconfig`, `hostname`, `sudo`, `nmcli` 사용 금지.
모든 명령은 **Windows PowerShell(관리자)** 에서 실행합니다. 기본 폴더는 `C:\Users\admin\Desktop\ALGN`입니다.

---

## 0. 준비

`key.sh`를 `C:\Users\admin\Desktop\ALGN\key.sh`로 저장합니다.

```powershell
$A='C:\Users\admin\Desktop\ALGN'; $o="$A\frozen"
New-Item -ItemType Directory -Force $o | Out-Null
```

## 1. 핵심 스레드 스택 + 전체 스택

```powershell
wsl -d Ubuntu-22.04 -u root -e sh -c "tr -d '\r' < /mnt/c/Users/admin/Desktop/ALGN/key.sh | sh"
```

- 화면에 [1]~[4]와 파일 목록, "완료"가 나오면 정상입니다.
- 특정 번호에서 1분 넘게 멈추면 Ctrl+C를 누르고, 몇 번에서 멈췄는지 알려 주세요.
- 생성 파일: `key_stacks.txt`, `02_ps_all.txt`, `03_all_stacks.txt`, `01_dmesg_now.txt`

## 2. 어제 뜬 blocked_full.txt에서 27078 찾기

```powershell
Select-String -Path C:\Users\admin\blocked_full.txt -Pattern 'pid:27078 ' -Context 0,40 | Out-File $o\blocked_27078.txt
Select-String -Path C:\Users\admin\blocked_full.txt -Pattern 'unregister_netdevice|waiting for|rescind|netvsc' | Out-File $o\blocked_netvsc.txt
```

## 3. 압축 후 업로드

```powershell
Compress-Archive $o\key_stacks.txt,$o\01_dmesg_now.txt,$o\02_ps_all.txt,$o\03_all_stacks.txt,$o\blocked_27078.txt,$o\blocked_netvsc.txt $A\P3_stacks.zip -Force
```

`P3_stacks.zip`을 GitHub `1015/ljs/`에 올립니다. 업로드 후에도 분석이 끝날 때까지 **재시작하지 않습니다.**

## 참고: 이 자료로 확인하려는 것

현재까지 확인된 사실 (P3_멈춤상태결과1/2 기준):

- `hv_vmbus_rescind` 작업 큐에서 **kworker/0:2(pid 27078)** 가 `vmbus_onmessage_work`를 처리하다 D 상태로 멈춰 있습니다.
- 그 뒤로 **VMBus 메시지 706개**가 처리되지 못하고 대기 중입니다.
- 시작 시점은 10/14 08:38:20.984, Hyper-V가 Wi-Fi 미러 NIC를 **Remove**한 순간입니다. 08:38:22의 Add도 대기열에 갇혀 반영되지 못했습니다.
- Windows/HNS 쪽 Remove/Add는 모두 성공(0x0)했습니다. 멈춘 곳은 **리눅스 커널의 장치 제거 경로(hv_vmbus → hv_netvsc)** 입니다.
- 그 밖의 D 상태 작업(addrconf_verify_work, ip, sudo, tcpdump)은 네트워크 잠금(RTNL)을 기다리는 피해자로 보입니다.

스택으로 확인할 것:

| 대상 | pid | 확인 내용 |
|---|---|---|
| kworker/0:2 | 27078 | 장치 제거 중 무엇을 기다리는가 (RTNL 대기 / eth2 참조 해제 대기 / Hyper-V 응답 대기) |
| kworker/u64:0 | 12 | addrconf 작업, RTNL 대기 여부 |
| rx-5 (muscat 컨테이너) | 9240 | eth2 소켓을 붙잡고 있는지 |
| tcpdump | 23589 | eth2 패킷 소켓 여부 |
| ip (최초 멈춤) | 30341 | 08:38:22 첫 피해자 |
| zenoh-bridge (좀비, 스레드 잔존) | 1629, 1943 | 남은 스레드가 커널 안에서 무엇을 하는가 |

결과에 따른 판단:

- 27078이 **커널 내부 대기**(완료 신호 대기, Hyper-V 응답 대기 등)에서 멈춰 있다 → **커널 버그**. WSL/커널 업데이트로 해결될 가능성이 높습니다.
- 27078이 **eth2 참조 해제**를 기다리고, 그 참조를 zenoh/컨테이너 스레드가 쥐고 있다 → **응용 프로그램 구조 문제**. 업데이트만으로는 재발할 수 있어 해당 프로세스의 처리 방식 수정이 필요합니다.
