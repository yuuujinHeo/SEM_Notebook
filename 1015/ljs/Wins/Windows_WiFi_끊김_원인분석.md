# Windows Wi-Fi 반복 끊김 — 원인 분석 (1차)

- 근거: P3(.60) 10/14 07:31~20:24 WLAN/System/NetworkProfile 이벤트(`WSL_Evidence_20261014_204116.zip`), Wi-Fi 드라이버 이벤트 XML(`wifi-disconnect-xml.zip`), 1013 5대 이벤트(`network-diagnostic.zip`)
- 이 문서에는 WSL 재시작·종료 명령이 없습니다.

## 1. 끊김이 일어나는 방식

Windows가 끊는 것은 무선 신호가 나빠서가 아닙니다. **"연결은 됐는데 데이터가 안 흐른다"고 판단한 Windows가 스스로 드라이버를 리셋**하는 것입니다.

```
재연결(보안 중지→시작→성공, 1초 이내)
  → 약 15초 동안 통신 불가
  → 4003 "제한된 연결 감지, 자동 복구"  +  Netwtw 8000 드라이버 Halt
  → 3~4초 뒤 완전 재연결(802.1X 인증 + 연결 성공)  → 정상화
```

## 2. 어떤 재연결이 문제인가 (P3, 10/14 하루, 재연결 70회)

| 재연결 종류 | 802.1X | 새 연결(11001/8001) | 드라이버 "Roam Complete"(7003) | 횟수 | 4003 발생 |
|---|---|---|---|---|---|
| 빠른 로밍 | 없음 | 없음 | **있음** | 35 | **0** |
| 재인증 로밍 | 있음 | 없음 | 있음 | 10 | 0 |
| 새 연결 | 있음 | 있음 | 없음 | 17 | 0 |
| **정체불명 재연결** | **없음** | **없음** | **없음** | **8** | **7** (07:42:50, 07:49:25, 08:38:05, 08:45:03, 19:29:32, 19:35:52, 19:44:42) |

- **PMK 캐시를 쓰는 빠른 로밍(35회)은 한 번도 문제가 없었습니다.** 앞서 의심했던 "빠른 로밍 = 문제" 가설은 틀렸습니다. 앞선 분석에서 7003 유무를 802.1X 재인증 유무로 잘못 해석했고, 여기서 바로잡습니다.
- 문제는 드라이버가 **로밍 완료(7003)를 남기지 않은 채 보안만 다시 맺은 재연결**입니다. 8번 중 7번이 15초 뒤 리셋으로 이어졌습니다.
- 드라이버 텔레메트리(7021)의 BSSID로 보면, 확인 가능한 3건 중 **2건(07:42:50, 07:49:25)은 같은 AP에 다시 붙은 것**입니다. 다른 AP로 옮겨간 로밍이 아니라는 뜻입니다.
- 1013 자료 5대에서도 같은 패턴입니다(7003 없는 재연결에서만 4003, 10~30%). 드라이버 버전이 다른 .206(Netwtw14 24.x)에서도 발생하므로, 특정 PC나 드라이버 문제일 가능성은 낮습니다.
- 암호화는 전부 WPA2-Enterprise / AES-GCMP-128로 같아서 구분 요인이 아닙니다.

## 3. 해석 (추정 — 확인 필요)

"같은 AP에 802.1X 없이 다시 붙은 뒤 데이터만 안 흐르는" 현상으로 볼 때, 후보는 다음과 같습니다.

| 후보 | 설명 | 근거 / 반론 |
|---|---|---|
| **A. AP/컨트롤러가 단말을 끊었다 다시 받음 → 데이터 경로 미복구** | AP가 단말을 내보낸 뒤(로드밸런싱, 밴드 스티어링, 스티키 클라이언트 처리 등) 빠른 재접속을 받았지만, 컨트롤러의 단말 정보(인가 상태, IP 바인딩, DHCP 스누핑 등)가 복구되지 않아 데이터를 막음. 리셋 후 완전 재연결과 DHCP를 거치면 정상화 | 5대 공통, 드라이버 무관, 리셋 후 즉시 정상화와 들어맞음 |
| B. 드라이버 내부 재연결 오류 | Intel 드라이버가 링크 이상 감지 후 자체 재연결했는데 키나 상태가 어긋남 | 서로 다른 드라이버 버전에서 똑같이 발생해 가능성 낮음 |

**현재 가장 유력한 것은 A입니다.** 다만 왜 재연결했는지(AP가 보낸 끊김 사유)와, 재연결 직후 ARP/DHCP가 실제로 막히는지를 확인해야 확정할 수 있습니다.

## 4. 확인 방법 (설정 변경 없음)

**4-1. 끊김 사유 코드 (1분, 바로 가능)**
```powershell
netsh wlan show wlanreport
Copy-Item C:\ProgramData\Microsoft\Windows\WlanReport\wlan-report-latest.html C:\Users\admin\Desktop\ALGN\
```
보고서에 세션마다 연결 해제 사유(Reason code)가 나옵니다. AP가 보낸 deauth/disassoc인지, 드라이버 자체 판단인지 구분할 수 있습니다.

**4-2. 다음 발생 때 무선 추적 + 패킷 (정상 운행 중인 호기 1대)**
```powershell
$A='C:\Users\admin\Desktop\ALGN'
netsh trace start scenario=wlan capture=yes maxsize=512 filemode=circular overwrite=yes report=disabled tracefile=$A\wlan.etl
ping.exe -t 10.249.138.1 | % { "{0:HH:mm:ss.fff} {1}" -f (Get-Date),$_ } | Out-File $A\ping-gw.log
```
4003이 1~2회 발생한 뒤에 정지합니다(ping 창은 Ctrl+C).
```powershell
netsh trace stop
```
- 재연결 직후 게이트웨이 ARP 요청에 응답이 없거나 ping이 끊김 → **AP/컨트롤러가 데이터를 막는 것**(후보 A)
- 4003 직전까지 ping 정상 → Windows 판단 문제

**4-3. 무선망 담당자 요청 (근거 갱신)**
- MAC `40:d1:33:cd:46:69`, 10/14 07:42:50, 07:49:25, 08:38:05, 08:45:03, 19:29:32, 19:35:52, 19:44:42
- 확인 요청:
  1. 해당 시각에 AP/컨트롤러가 단말을 deauth/disassoc 했는지와 그 사유(로드밸런싱, 밴드 스티어링, 클라이언트 정리 정책 등)
  2. 재접속 직후 약 15초 동안 단말 상태(인가 상태, IP 바인딩, DHCP 스누핑 테이블)
  3. 단말 MAC의 BSSID 이력 (07:42:50, 07:49:25은 같은 AP 재접속으로 보임)
