# [삼성전자 메탈 A동] 공정3호기 FRS 재연결 실패 원인 분석 및 해결 방안  
  
- 작성일: 2026-10-15  
- 장애 발생일: 2026-10-04, 2026-10-14  
- 대상: 공정3호기 (SEC_Process_2)  
- 환경: Windows / WSL2 Ubuntu 22.04 / Muscat / Zenoh / FRS  
- 분석 상태: 장애 현상 확인, 근본 원인 조사 중  
- 조치 원칙: 증거 확보 → 원인 분석 → 서비스 영향 확인 → 복구 → 재발 방지  
  
---  
  
# 1. 장애 요약  
  
## 1.1 문제 상황  
  
공정3호기에서 Intel Wi-Fi 어댑터 리셋 이후 WSL2 내부 네트워크 통신이 복구되지 않아 Muscat과 FRS 간 연결이 장시간 끊기는 현상이 발생했다.  
  
일반적으로 Wi-Fi 리셋 이후 FRS에 자동 재연결되지만, 특정 상황에서는 WSL2의 네트워크 처리 경로가 정체되면서 재연결에 실패한다.  
  
### 주요 증상  
  
- Windows → FRS TCP 연결 정상  
- WSL → FRS TCP 연결 실패  
- WSL `ip addr`, `ip route` 명령어 무한 대기  
- 다수의 `ip` 프로세스 D 상태  
- `timeout`, `kill`로도 D 상태 프로세스가 즉시 종료되지 않음  
- `/proc/PID/stack` 조회 무한 대기  
- Zenoh Bridge 종료 프로세스 확인  
- Muscat 연결 상태 `DISCONNECT`  
- FRS 재연결 실패 지속  
  
## 1.2 핵심 판단  
  
**Windows Wi-Fi 리셋을 계기로 WSL2 mirrored 네트워크의 커널 처리 경로가 정체되었을 가능성이 가장 높다.**  
  
다만 RTNL 락을 실제로 점유한 프로세스와 최초 정체 함수는 아직 확인되지 않았다.  
  
따라서 현재는 다음과 같이 구분한다.  
  
| 구분 | 판단 |  
|---|---|  
| 확인된 현상 | WSL RTNETLINK 관련 프로세스 다수 D 상태 |  
| 확인된 통신 장애 | WSL → FRS `No route to host` |  
| 유력한 트리거 | Intel Wi-Fi 리셋 4003/8000 |  
| 유력한 원인 | WSL mirrored 네트워크 처리 정체 |  
| 미확정 사항 | RTNL 락 점유자 및 최초 커널 정체 원인 |  
| 우선 복구 방안 | 로그 확보 후 WSL 재시작 |  
| 재발 방지 후보 | NAT 전환, Wi-Fi 로밍 및 드라이버 개선 |

# 4. 네트워크 진단 결과  
  
## 4.1 Windows → FRS


결과:  
  
```text

```  
  
### 판단

## 4.2 WSL → FRS  
  
명령어:  
  
```bash  
timeout -k 2s 5s bash -c \  
'echo > /dev/tcp/10.244.201.165/7447'  
  
echo "tcp_exit=$?"  
```  
  
결과:  
  
```text  
bash: connect: No route to host  
tcp_exit=1  
```  
  
### 판단  
  
WSL에서 FRS까지 TCP 연결이 실패한다.  
  
Windows에서는 동일 목적지로 연결에 성공하므로 Windows와 WSL의 네트워크 처리 상태에 차이가 있다.  
  
## 4.3 WSL 라우팅 테이블  
  
명령어:  
  
```bash  
cat /proc/net/route  
```  
  
결과:  
  
| 인터페이스 | Gateway | Metric |  
|---|---|---|  
| eth2 | 10.249.138.1 | 60 |  
| eth0 | 10.108.2.1 | 281 |  
| eth1 | 192.168.0.1 | 291 |  
  
### 판단  
  
WSL 내부에 기본 게이트웨이가 존재한다.  
  
따라서 기본 게이트웨이 누락이 직접 원인은 아니다.  
  
## 4.4 ARP  
  
WSL:  
  
```text  
10.249.138.1 at <incomplete> on eth2  
```  
  
Windows:  
  
```text  
10.249.138.1 at 4c-ae-a3-88-be-01  
```  
  
### 판단  
  
Windows는 Wi-Fi 게이트웨이의 MAC 주소를 확인한다.  
  
WSL eth2에서는 ARP 확인이 완료되지 않았다.  
  
다만 mirrored 네트워크에서는 Windows와 WSL의 이웃 테이블 처리 방식이 다를 수 있어 이것만으로 장애 원인을 확정할 수는 없다.

# 5. WSL 커널 네트워크 정체  
  
## 5.1 문제 명령어  
  
```bash  
ip addr  
ip route  
ip -4 route  
ip -br link  
```  
  
증상:  
  
- 명령어가 종료되지 않음  
- 출력 없이 대기  
- timeout 이후에도 종료되지 않음  
- D 상태 프로세스 누적  
  
## 5.2 프로세스 상태  
  
명령어:  
  
```bash  
ps -eo pid,ppid,stat,wchan:25,comm |  
grep -E 'ip|timeout|STAT'  
```  
  
주요 결과:  
  
```text  
D   rtnl_dumpit          ip  
D   rtnetlink_rcv_msg     ip  
D+  rtnl_dumpit          ip  
D+  rtnetlink_rcv_msg     ip  
```  
  
### 분석  
  
`ip` 명령어는 RTNETLINK를 통해 Linux 커널의 네트워크 정보를 조회한다.  
  
현재 다수의 요청이 커널 내부에서 정상적으로 완료되지 않는다.  
  
RTNL 락 경합 또는 네트워크 처리 작업의 장시간 정체가 의심된다.  
  
단, 실제 락 점유자는 아직 확인되지 않았다.

# 6. 커널 스택 조회 무한 대기 현상  
  
## 6.1 추가로 확인된 문제  
  
커널 스택 분석을 위해 `/proc/PID/stack`을 조회했으나 명령어가 종료되지 않는 현상이 발생했다.  
  
예시:  
  
```bash  
sudo cat /proc/30341/stack  
```  
  
증상:  
  
- 명령어 실행 후 출력 없음  
- 프롬프트 복귀하지 않음  
- 스택 정보 확보 실패  
  
### 판단  
  
커널 스택 조회 경로에서도 장시간 대기가 발생했을 가능성이 있다.  
  
다만 다음 두 상황은 구분해야 한다.  
  
1. `sudo` 자체가 멈춘 경우  
2. `/proc/PID/stack` 조회가 멈춘 경우  
  
현재 결과만으로 둘 중 어느 단계에서 멈췄는지 확정할 수 없다.  
  
## 6.2 동일 명령어 반복 실행 금지  
  
현재 반복하지 말아야 할 명령어:  
  
```bash  
ip route  
ip addr  
sudo cat /proc/30341/stack  
```  
  
이유:  
  
- 새로운 D 상태 프로세스가 누적될 수 있음  
- timeout으로 종료되지 않을 수 있음  
- 기존 장애 원인 분석에 도움이 되지 않을 수 있음

# 7. 커널 스택 우회 진단  
  
## 7.1 sudo 응답 확인  
  
먼저 sudo 명령어가 정상적으로 실행되는지 확인한다.  
  
```bash  
timeout -k 2s 3s sudo -n true  
  
echo "sudo_exit=$?"  
```  
  
결과 해석:  
  
| 결과 | 의미 |  
|---|---|  
| 0 | sudo 실행 성공 |  
| 124 | 제한 시간 초과 |  
| 기타 | 권한 또는 다른 오류 |  
  
주의:  
  
대상 프로세스가 D 상태에 들어가면 timeout으로도 종료되지 않을 수 있다.  
  
sudo가 멈춘다면 추가적인 sudo 명령어 실행을 중단한다.  
  
## 7.2 SysRq blocked task 덤프  
  
sudo가 정상인 경우에만 진행한다.  
  
```bash  
timeout -k 2s 5s sudo -n sh -c \  
'echo w > /proc/sysrq-trigger'  
  
echo "sysrq_exit=$?"  
```  
  
### 명령어 의미  
  
`echo w > /proc/sysrq-trigger`  
  
Linux 커널에 blocked task 정보를 로그로 출력하도록 요청한다.  
  
특징:  
  
- WSL을 재시작하지 않음  
- blocked task 스택 확인 목적  
- 커널 로그에 결과 기록  
- 커널 상태에 따라 명령어가 멈출 수 있음  
  
주의:  
  
- 관리자 권한 필요  
- 커널의 SysRq 지원 여부 확인 필요  
- 커널 로그 출력량 증가 가능  
- 운영 환경에서 진단 영향 확인 후 실행  
  
## 7.3 커널 로그 확인  
  
```bash  
timeout -k 2s 5s dmesg | tail -150  
  
echo "dmesg_exit=$?"  
```  
  
확인 키워드:  
  
```text  
Call Trace  
rtnl  
rtnetlink  
netvsc  
rndis  
vmbus  
hv_  
veth  
br_  
nf_  
```  
  
## 7.4 전체 작업 스택 덤프  
  
blocked task 덤프에서 원인을 찾지 못한 경우 검토한다.  
  
```bash  
sudo -n sh -c 'echo t > /proc/sysrq-trigger'  
```  
  
주의:  
  
전체 작업 스택 덤프는 매우 많은 로그를 발생시킬 수 있다.  
  
로그 저장 공간과 수집 경로를 확인한 뒤 실행한다.

# 8. 커널 스택 결과별 분석 방향  
  
## 유형 A. Hyper-V / 가상 네트워크  
  
스택에서 다음 함수가 관찰되는 경우:  
  
```text  
netvsc  
rndis  
vmbus  
hv_  
```  
  
조사 대상:  
  
- WSL mirrored 네트워크  
- Hyper-V 가상 네트워크  
- Windows Wi-Fi 리셋  
- Windows와 WSL 간 네트워크 변경 동기화  
  
### 판단  
  
WSL 가상 네트워크 경로의 정체 가능성이 높아진다.  
  
단, 함수명만으로 WSL 버그가 확정되는 것은 아니다.  
  
## 유형 B. Docker 네트워크  
  
스택에서 다음 함수가 관찰되는 경우:  
  
```text  
veth  
br_  
nf_  
```  
  
조사 대상:  
  
- Docker 브리지  
- veth 인터페이스  
- netfilter  
- 컨테이너 네트워크 네임스페이스  
  
### 판단  
  
Docker 네트워크 처리 경로가 정체에 관여했을 가능성이 있다.  
  
이 경우 NAT 전환만으로 해결되지 않을 수 있다.  
  
## 유형 C. 원인 프로세스 확인 불가  
  
blocked task 덤프에서 RTNL 락 점유자가 확인되지 않을 수 있다.  
  
이 경우 전체 작업 덤프와 Windows 호스트 로그를 함께 분석해야 한다.

# 9. SysRq도 무한 대기하는 경우  
  
## 9.1 판단 기준  
  
| 결과 | 판단 |  
|---|---|  
| sudo부터 무한 대기 | sudo/PAM 또는 커널 작업 정체 가능성 |  
| sudo 정상, stack 조회 멈춤 | 스택 조회 경로 정체 가능성 |  
| SysRq 요청도 멈춤 | 커널 진단 경로 정체 가능성 |  
| SysRq 성공, dmesg 멈춤 | 커널 로그 조회 경로 문제 가능성 |  
  
## 9.2 조치  
  
SysRq까지 무한 대기하면 WSL 내부 진단을 반복하지 않는다.  
  
이후 Windows 호스트에서 확보 가능한 로그로 분석을 전환한다.  
  
### Windows Wi-Fi 이벤트 확보  
  
PowerShell:  
  
```powershell  
Get-WinEvent -ListLog *WLAN* |  
Select-Object LogName,RecordCount  
```  
  
Windows WLAN 이벤트 로그의 실제 이름을 확인한 뒤 해당 로그를 수집한다.  
  
### Windows 시스템 이벤트 확보  
  
```powershell  
Get-WinEvent -FilterHashtable @{  
    LogName='System'  
    StartTime=[datetime]'2026-10-14 08:30:00'  
    EndTime=[datetime]'2026-10-14 08:50:00'  
} |  
Select-Object TimeCreated,ProviderName,Id,LevelDisplayName,Message |  
Format-List  
```  
  
확인 항목:  
  
- Intel Wi-Fi 관련 이벤트  
- 네트워크 어댑터 리셋  
- Hyper-V 관련 오류  
- WSL 관련 오류  
- 장애 발생 전후 이벤트  
  
### WSL 관련 이벤트 로그 확인  
  
```powershell  
Get-WinEvent -ListLog '*Hyper-V*','*Lxss*' `  
    -ErrorAction SilentlyContinue |  
Select-Object LogName,RecordCount  
```  
  
실제 존재하는 로그를 확인한 후 장애 시각의 이벤트를 조회한다.

# 10. Muscat / Zenoh 상태  
  
## 10.1 Zenoh Bridge  
  
확인 결과:  
  
```text  
[zenoh-bridge-ro] <defunct>  
```  
  
해당 프로세스는 종료된 좀비 프로세스다.  
  
정상 실행 중인 Zenoh Bridge가 아니다.

# 13. NAT 전환 시험  
  
## 13.1 목적  
  
WSL mirrored 네트워크가 Wi-Fi 리셋 이후 정체되는 문제를 회피할 수 있는지 검증한다.  
  
## 13.2 전환 전 확인  
  
- Windows → WSL localhost 접근  
- 외부 → 로봇 PC 인바운드 연결  
- Muscat HTTP 3000  
- Zenoh TCP 7447  
- Docker 포트 매핑  
- FRS 연결  
- FMS 연결  
- 로봇 API 8180  
- mDNS/Avahi  
  
## 13.3 기존 설정 백업  
  
PowerShell:  
  
```powershell  
Copy-Item "$env:USERPROFILE\.wslconfig" `  
"$env:USERPROFILE\.wslconfig.backup"  
```  
  
## 13.4 NAT 설정  
  
```ini  
[wsl2]  
networkingMode=nat  
dnsTunneling=true  
```  
  
설정 적용:  
  
```powershell  
wsl --shutdown  
```  
  
### 주의  
  
- 운영 중 즉시 변경하지 않음  
- 기존 설정 백업 필수  
- NAT 전환 후 외부 인바운드 통신 별도 검증  
- Docker 포트 매핑 확인  
- Windows 포트포워딩 필요 여부 확인  
- TCP/UDP 사용 프로토콜 확인  
  
## 13.5 성공 기준  
  
Wi-Fi 리셋 발생 이후에도:  
  
1. WSL 네트워크 정상  
2. `ip route` 정상  
3. FRS TCP 연결 정상  
4. Muscat-FRS 자동 재연결  
5. Muscat-FMS 통신 정상  
6. AMR 상태 송수신 정상  
  
단기간 정상 동작만으로 재발 방지가 입증되었다고 판단하지 않는다.

# 15. 최종 결론  
  
## 확인된 사실  
  
- Windows Wi-Fi 리셋 직후 WSL 네트워크 명령어 정체 발생  
- Windows → FRS TCP 연결 정상  
- WSL → FRS TCP 연결 실패  
- WSL 기본 게이트웨이 존재  
- RTNETLINK 관련 프로세스 다수 D 상태  
- 커널 스택 조회 명령어도 무한 대기  
- Muscat 상태 DISCONNECT  
- Zenoh Bridge 종료 프로세스 확인  
  
## 가장 유력한 원인  
  
Windows Wi-Fi 리셋 과정에서 WSL2 mirrored 네트워크의 커널 처리 경로가 정체되는 문제.  
  
## 아직 확인되지 않은 사항  
  
- RTNL 락 실제 점유자  
- 최초 커널 정체 함수  
- Hyper-V와 Docker 네트워크의 관여 여부  
- Wi-Fi 리셋과 커널 정체의 직접 인과관계  
- NAT 전환의 재발 방지 효과  
  
## 권장 조치 순서  
  
1. sudo 응답 확인  
2. SysRq blocked task 덤프 시도  
3. SysRq도 멈추면 WSL 내부 진단 중단  
4. Windows 이벤트 로그 확보  
5. Docker/Muscat 로그 확보  
6. 서비스 영향 확인 후 WSL 재시작  
7. FRS 연결 및 Muscat 통신 복구 확인  
8. NAT 전환 시험  
9. Wi-Fi 드라이버 및 AP 로밍 정책 개선  
  
**핵심 결론: Wi-Fi 리셋은 유력한 장애 트리거이고, WSL2 RTNETLINK 처리 정체는 확인된 장애 현상이다. 커널 스택 조회까지 멈추는 상황에서는 무리한 추가 진단보다 Windows 로그 확보 후 통제된 WSL 재시작을 우선 검토해야 한다.**
