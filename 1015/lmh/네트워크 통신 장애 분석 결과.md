# WSL2 / Muscat / Zenoh / FMS 통신 장애 분석 보고서

- 분석일: 2026-10-15
- 대상: Windows PC / WSL2 Ubuntu 22.04
- WSL 버전: 2.7.8.0
- WSL 커널: 6.18.33.1-1
- 네트워크 모드: mirrored
- 장애 상태: 원인 분석 완료 전, 복구 조치 필요

---

# 1. 최종 진단 요약

## 1.1 현재 확인된 문제

SI-FMS 통신은 정상이나 Muscat-FMS 통신이 실패하고 있다.

Windows 자체에서는 FRS 서버의 TCP 7447 포트에 정상적으로 연결된다.

반면 WSL2에서는 네트워크 관련 명령어가 종료되지 않고 다수의 프로세스가 커널 D 상태로 누적되어 있다.

### 진단 결과

| 검사 항목 | 결과 | 판단 |
|---|---|---|
| SI → FMS | 정상 | 기존 통신 유지 |
| Muscat → FMS | 실패 | 장애 발생 |
| Windows → FRS:7447 | 성공 | 외부 TCP 경로 정상 |
| WSL 기본 게이트웨이 | 존재 | 게이트웨이 누락 아님 |
| WSL ARP 테이블 | 일부 정상 | MOXA MAC 확인 |
| WSL ip route | 무한 대기 | 비정상 |
| WSL ip addr | 무한 대기 | 비정상 |
| WSL ip 프로세스 | 다수 D 상태 | 커널 처리 정체 |
| Windows localhost:7447 | 실패 | 로컬 TCP 서비스 접근 불가 |
| Windows localhost:3000 | 실패 | Muscat HTTP 접근 불가 |

## 1.2 가장 유력한 원인

WSL2 Linux 커널의 RTNETLINK 네트워크 처리 경로가 정체되어 있는 상태.

특히 다음 커널 함수에서 다수의 ip 프로세스가 대기 중이다.

```text
rtnl_dumpit
rtnetlink_rcv_msg
```

이는 네트워크 인터페이스 및 라우팅 정보 조회 요청이 커널 내부에서 정상적으로 완료되지 않는 상황을 의미한다.

RTNL 락 경합 또는 관련 커널 작업의 장시간 점유가 의심된다.

다만 현재 로그만으로 최초 장애를 유발한 프로세스나 커널 결함을 확정할 수는 없다.

## 2.1 Windows 네트워크 인터페이스

| 인터페이스 | IP 주소 | 게이트웨이 | 상태 |
|---|---|---|---|
| RB&Vision | 10.108.2.101 | 10.108.2.1 | UP |
| Wi-Fi | 10.249.138.60 | 10.249.138.1 | UP |
| Fastech | 192.168.0.160 | 192.168.0.1 | UP |
| vEthernet | 172.25.48.1 | 없음 | UP |

현재 Windows에는 3개의 기본 게이트웨이가 존재한다.

```text
10.108.2.1

10.249.138.1
```

### 기본 경로 메트릭

```text
0.0.0.0/0 → 10.249.138.1   Metric 45
0.0.0.0/0 → 10.108.2.1     Metric 281
0.0.0.0/0 → 192.168.0.1    Metric 291
```

Windows는 현재 Wi-Fi의 기본 경로를 우선 사용한다.

다만 목적지별로 더 구체적인 경로가 있다면 해당 경로가 우선한다.

# 3. WSL 네트워크 분석

## 3.1 WSL 네트워크 모드

현재 설정:

```ini
[wsl2]
networkingMode=mirrored
dnsTunneling=true
firewall=false
```

mirrored 모드는 Windows 네트워크 인터페이스를 WSL 환경에 반영하는 방식이다.

따라서 WSL 내부에도 여러 네트워크 인터페이스 및 기본 경로가 존재할 수 있다.

## 3.2 WSL 라우팅 테이블

실행 명령어:

```bash
cat /proc/net/route
```

실제 결과:

```text
Iface  Destination  Gateway   Metric

eth2   00000000     018AF90A  60
eth0   00000000     01026C0A  281
eth1   00000000     0100A8C0 291
```

Gateway 필드는 16진수 리틀 엔디언 형식이다.

변환 결과:

| 인터페이스 | 게이트웨이 | Metric |
|---|---|---|
| eth2 | 10.249.138.1 | 60 |
| eth0 | 10.108.2.1 | 281 |
| eth1 | 192.168.0.1 | 291 |

### 판단

WSL 내부에도 기본 게이트웨이가 정상적으로 등록되어 있다.

가장 낮은 Metric은 eth2의 60이다.

따라서 일반적인 기본 경로 선택 기준으로는 다음 경로가 우선된다.

```text
WSL
 |
 v
eth2
 |
 v
10.249.138.1
 |
 v
FRS
10.244.201.165
```

단, 실제 패킷 전달 성공 여부는 별도로 검증해야 한다.

### 중요한 결론

WSL 네트워크가 IP와 게이트웨이를 전혀 인식하지 못하는 상황은 아니다.

라우팅 정보 자체는 커널에 존재한다.

문제는 ip 명령어를 통한 RTNETLINK 조회가 정상적으로 완료되지 않는다는 점이다.

# 4. ARP 테이블 분석

## 4.1 WSL ARP 결과

```text
10.108.2.1
00:90:e8:de:d8:01
eth0

10.108.2.2
cc:82:7f:a7:68:d3
eth0

10.249.138.1
<incomplete>
eth2
```

### 판단

WSL은 eth0에서 10.108.2.1과 10.108.2.2의 MAC 주소를 확인하고 있다.

따라서 WSL이 모든 네트워크 정보를 인식하지 못하는 것은 아니다.

다만 eth2에서 10.249.138.1의 ARP 상태는 incomplete이다.

이는 해당 인터페이스에서 이웃 장비의 MAC 주소 확인이 완료되지 않았음을 의미한다.

## 4.2 Windows ARP 결과

```text
10.249.138.1
4c-ae-a3-88-be-01
```

Windows에서는 Wi-Fi 게이트웨이 MAC 주소가 정상적으로 확인된다.

### 차이점

Windows:

```text
10.249.138.1 → MAC 확인
```

WSL:

```text
10.249.138.1 → incomplete
```

### 해석

mirrored 네트워크 환경에서 Windows와 WSL의 ARP 또는 이웃 테이블 표현은 다를 수 있다.

따라서 이 차이만으로 WSL의 Wi-Fi 통신 장애를 확정할 수 없다.

그러나 WSL에서 FRS 연결까지 실패한다면 추가로 조사해야 할 단서다.

# 5. 가장 중요한 장애 증거

## 5.1 ip 명령어가 D 상태로 누적

실행 명령어:

```bash
ps -eo pid,ppid,stat,wchan:25,comm |
grep -E 'ip|timeout|STAT'
```

주요 결과:

```text
D   rtnl_dumpit         ip
D   rtnetlink_rcv_msg    ip
D+  rtnl_dumpit         ip
D+  rtnetlink_rcv_msg    ip
```

다수의 ip 프로세스가 동일한 커널 네트워크 처리 경로에서 대기하고 있다.

### 의미

ip 명령어는 네트워크 정보를 조회하기 위해 Linux 커널에 RTNETLINK 요청을 보낸다.

현재 해당 요청이 정상적으로 완료되지 않는다.

이로 인해 다음 명령어들이 멈춘다.

```bash
ip addr
ip route
ip link
```

### timeout이 작동하지 않는 이유

D 상태는 인터럽트 불가능한 커널 대기 상태다.

프로세스가 이 상태에 있으면 종료 신호가 즉시 처리되지 않을 수 있다.

따라서 다음 명령어도 종료되지 않는다.

```bash
timeout 5 ip -4 route
```

이것은 단순한 네트워크 연결 실패와 구분되는 커널 수준의 장애 징후다.

# 6. Muscat / Zenoh 로컬 연결 분석

## 6.1 로컬 Zenoh TCP 검사

실행 명령어:

```powershell
Test-NetConnection 127.0.0.1 -Port 7447
```

결과:

```text
TcpTestSucceeded : False
```

### 판단

Windows의 127.0.0.1:7447에서는 TCP 연결이 수락되지 않았다.

가능한 원인:

1. Zenoh 프로세스가 실행되지 않음
2. Zenoh가 다른 IP에 바인딩되어 있음
3. Zenoh가 WSL 내부에서 실행되지만 Windows localhost에 노출되지 않음
4. TCP가 아닌 다른 프로토콜 또는 포트를 사용
5. WSL 네트워크 장애로 포트 접근이 정상적으로 이루어지지 않음

이 결과만으로 Zenoh 프로세스가 종료되었다고 확정할 수는 없다.

## 6.2 로컬 Muscat HTTP 검사

실행 명령어:

```powershell
curl.exe -i --max-time 5 http://localhost:3000/common/docs
```

결과:

```text
curl: (7) Failed to connect to localhost port 3000
```

### 판단

Windows localhost:3000에서 Muscat HTTP 서비스에 접근할 수 없다.

가능한 원인:

1. Muscat 프로세스 미실행
2. Muscat HTTP 서버 미기동
3. 다른 포트에서 실행
4. WSL 내부에서만 바인딩
5. WSL 네트워크 또는 localhost 포워딩 문제

### 중요

현재 확인된 사실은 로컬 포트 연결 실패다.

Muscat과 Zenoh의 실제 실행 여부는 아직 확인되지 않았다.

# 7. 원인 우선순위

## 1순위: WSL2 RTNETLINK 처리 정체

근거:

- 다수의 ip 프로세스 D 상태
- rtnl_dumpit 대기
- rtnetlink_rcv_msg 대기
- timeout 종료 실패
- 일반 Linux 명령어 정상

현재 가장 강하게 확인된 비정상 현상이다.

## 2순위: WSL mirrored 네트워크 관련 문제

근거:

- networkingMode=mirrored
- Windows에는 3개의 네트워크 인터페이스와 기본 게이트웨이가 존재
- WSL에서도 여러 기본 경로 확인
- Windows와 WSL의 ARP 상태 차이

다중 네트워크 인터페이스와 mirrored 네트워크 처리 간 상호작용을 조사할 필요가 있다.

다만 mirrored 모드 자체가 원인이라는 증거는 아직 없다.

## 3순위: Muscat / Zenoh 서비스 문제

근거:

- Windows localhost:7447 실패
- Windows localhost:3000 실패
- Muscat-FMS 통신 실패

서비스 미실행, 바인딩 문제, 포트 노출 문제를 구분해야 한다.

## 4순위: FRS 라우팅 문제

Windows → FRS는 정상이다.

WSL의 기본 경로도 존재한다.

따라서 게이트웨이 누락보다는 WSL 내부 TCP 연결 여부를 확인하는 것이 우선이다.

# 8. 지금 바로 해야 할 작업

## STEP 1. WSL에서 FRS TCP 연결 확인

현재 ip 명령어가 멈추므로 사용하지 않는다.

WSL Ubuntu에서 실행:

```bash
timeout -k 2s 5s bash -c \
'echo > /dev/tcp/10.244.201.165/7447'

echo "tcp_exit=$?"
```

결과:

```text
tcp_exit=0
```

이면 WSL에서 FRS TCP 연결 성공.

```text
tcp_exit=124
```

이면 제한 시간 초과.

그 외 오류는 메시지와 함께 확인한다.

주의:

이 명령어는 Bash TCP 기능을 사용한다.
Zenoh 프로토콜 자체를 검증하는 것은 아니다.

## STEP 2. Muscat / Zenoh 프로세스 확인

WSL에서 실행:

```bash
ps aux | grep -Ei 'muscat|zenoh'
```

Docker 사용 시:

```bash
docker ps --no-trunc
```

확인 사항:

- Muscat 프로세스 존재 여부
- Zenoh 프로세스 존재 여부
- 컨테이너 실행 상태
- 포트 매핑 설정

주의:

docker ps도 멈춘다면 반복 실행하지 않고 해당 사실을 기록한다.

## STEP 3. Windows에서 포트 리스닝 확인

PowerShell:

```powershell
Get-NetTCPConnection -LocalPort 7447,3000 `
    -ErrorAction SilentlyContinue |
    Select-Object LocalAddress,LocalPort,State,OwningProcess
```

목적:

Windows에서 실제로 해당 포트를 리스닝하는 프로세스가 있는지 확인한다.

리스닝이 없다면 Windows 로컬 포트에서 연결을 수락하는 서비스가 없다는 의미다.

단, WSL 내부의 리스닝 상태까지 완전히 설명하지는 못한다.

## STEP 4. WSL 내부 포트 확인

WSL Ubuntu:

```bash
cat /proc/net/tcp
cat /proc/net/tcp6
```

7447의 16진수 포트는 1D17이다.

3000의 16진수 포트는 0BB8이다.

확인 대상:

```text
:1D17
:0BB8
```

TCP 상태 0A는 LISTEN을 의미한다.

단, 컨테이너가 별도 네트워크 네임스페이스를 사용하는 경우 해당 네임스페이스의 포트는 여기서 보이지 않을 수 있다.

## STEP 5. 커널 로그 확보

WSL Ubuntu:

```bash
sudo dmesg -T > ~/wsl-kernel-dmesg.txt
```

로그에서 확인할 항목:

```text
hung task
blocked for more than
rtnl
rtnetlink
netdev
watchdog
```

로그 조회가 멈추면 추가 실행을 중단한다.

# 10. 재발 시 추가 해결 방안

## 10.1 WSL 업데이트 검토

현재 버전:

```text
WSL 2.7.8.0
Kernel 6.18.33.1-1
```

Windows PowerShell:

```powershell
wsl --update
```

주의:

운영 중인 시스템에서는 업데이트로 인한 호환성 영향을 검토한 후 진행한다.

## 10.2 mirrored 모드 영향 검증

현재 설정:

```ini
[wsl2]
networkingMode=mirrored
dnsTunneling=true
firewall=false
```

별도 점검 시간에 NAT 모드와 비교 검증할 수 있다.

단, 네트워크 모드를 변경하면 다음 동작이 달라질 수 있다.

- Windows와 WSL의 IP 구성
- localhost 접근
- Zenoh 연결
- Docker 포트 노출
- 사내망 접근 경로

따라서 운영 환경에서 즉시 변경하지 않는다.

## 10.3 불필요한 기본 게이트웨이 검토

현재 Windows에는 3개의 기본 게이트웨이가 존재한다.

```text
10.108.2.1
192.168.0.1
10.249.138.1
```

현재는 Wi-Fi 경로가 가장 우선된다.

다만 다중 기본 게이트웨이는 환경 변화에 따라 의도하지 않은 경로 선택에 영향을 줄 수 있다.

필요하지 않은 게이트웨이가 있는지 네트워크 설계 기준과 비교한다.

주의:

현재 설정을 임의로 삭제하거나 변경하지 않는다.

# 12. 최종 결론

현재 장애는 단순한 게이트웨이 누락으로 설명되지 않는다.

Windows와 WSL 모두 기본 게이트웨이를 가지고 있으며 Windows에서 FRS TCP 연결도 성공한다.

반면 WSL 내부에서는 다수의 ip 프로세스가 RTNETLINK 관련 커널 함수에서 D 상태로 대기하고 있다.

따라서 가장 먼저 해결해야 할 문제는 WSL2 커널 네트워크 처리 정체다.

그러나 Muscat과 Zenoh의 실제 실행 상태가 확인되지 않았으므로 해당 장애가 Muscat-FMS 통신 실패의 직접적인 원인이라고 단정할 수는 없다.

권장 순서:

1. WSL → FRS TCP 연결 확인
2. Muscat / Zenoh 프로세스 확인
3. 커널 로그 확보
4. 서비스 영향 검토
5. WSL 재시작
6. 네트워크 및 서비스 재검증
7. 재발 시 mirrored 모드와 커널 버전 조사

현재 가장 유력한 원인:
WSL2 RTNETLINK 커널 처리 정체

추가로 확인해야 할 문제:
Muscat 및 Zenoh 로컬 서비스 접근 실패
