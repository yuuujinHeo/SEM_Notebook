- 장애 상태: 원인 분석 중

# 1. 문제 상황

## 1.1 시스템 통신 현황

| 통신 구간 | 상태 | 비고 |
|---|---|---|
| ACS - SI - FMS | 일부 정상 | SI-FMS 통신 확인 |
| SI → FMS | 정상 | 통신 가능 |
| Muscat → FMS | 비정상 | 통신 실패 |
| Muscat → FRS | 확인 필요 | 10.244.201.165:7447 |
| Windows → FRS | 확인 필요 | TCP 연결 검사 필요 |
| WSL → FRS | 확인 필요 | 네트워크 명령어 응답 없음 |
| Windows → 로컬 Zenoh | 확인 필요 | 127.0.0.1:7447 |
| Windows → 로컬 Muscat | 확인 필요 | localhost:3000 |

### 통신 구조

```text
                   ACS
                    |
                    v
                   SI
                    |
                    v
                   FMS
                    ^
                    |
               통신 실패
                    |
                 Muscat
                    |
                  Zenoh
                    |
               WSL2 Ubuntu
                    |
             Windows Network
                    |
                Wi-Fi / MOXA
                    |
                 FRS Server
             10.244.201.165:7447
```

※ 위 그림은 장애 구간을 설명하기 위한 개략도이다.
※ 실제 Muscat, Zenoh, FMS, FRS 간 통신 방향과 포트는 설정 파일로 확인해야 한다.

## 1.2 주요 장애 증상

Windows PC 내부 WSL2 Ubuntu에서 네트워크 관련 명령어 실행 시 응답하지 않는 현상 발생.

문제 명령어:

```bash
ifconfig
ip addr
ip -4 addr
ip route
ip -4 route
ip -br link
```

증상:

- 명령어 실행 후 출력 없이 대기
- 터미널 프롬프트가 돌아오지 않음
- timeout 명령어로 실행해도 제한 시간이 지난 후 종료되지 않음
- 여러 ip 프로세스가 D 상태로 누적됨
- WSL 내부 네트워크 상태를 정상적으로 조회할 수 없음

단, 이것만으로 WSL에 IP 주소나 게이트웨이가 없다고 단정할 수는 없다.

# 2. 현재까지 확인한 내용

## 2.1 Linux 기본 명령어 정상

실행 명령어:

```bash
echo TEST
date
```

결과:

```text
TEST
Wed Oct 14 21:42:39 KST 2026
```

판단:

- WSL 자체가 완전히 멈춘 것은 아님
- 기본적인 프로세스 실행은 가능
- 네트워크 관련 커널 작업에서 문제가 발생할 가능성이 높음

## 2.2 ip 프로세스 상태 확인

실행 명령어:

```bash
ps -eo pid,ppid,stat,wchan:25,comm | grep -E 'timeout|ip|STAT'
```

주요 결과:

```text
PID     PPID    STAT    WCHAN                 COMMAND

30341   314     D       rtnl_dumpit           ip
237456  237329  D+      rtnetlink_rcv_msg      ip
242289  242274  D+      rtnl_dumpit           ip
246096  246080  S+      sigsuspend            timeout
246097  246096  D+      rtnetlink_rcv_msg      ip
246618  246617  D+      rtnetlink_rcv_msg      ip
246989  246988  D+      rtnl_dumpit           ip
304620  304619  D       rtnl_dumpit           ip
```

실제 출력에서는 이외에도 다수의 ip 프로세스가 D 상태로 확인됨.

### STAT 의미

| 상태 | 의미 |
|---|---|
| R | 실행 중 |
| S | 인터럽트 가능한 대기 |
| D | 인터럽트 불가능한 커널 대기 |
| T | 중지 |
| Z | 좀비 프로세스 |

### WCHAN 의미

rtnl_dumpit

- 커널의 네트워크 정보 조회 처리와 관련된 함수
- 네트워크 인터페이스 또는 라우팅 정보 조회 중 대기하는 상황에서 나타날 수 있음

rtnetlink_rcv_msg

- 커널이 RTNETLINK 요청을 처리하는 경로
- 네트워크 정보 조회 또는 설정 요청 처리 중 정체되었을 가능성

### 판단

다수의 ip 프로세스가 RTNETLINK 관련 커널 함수에서 D 상태로 대기하고 있다.

따라서 단순한 게이트웨이 미설정보다는 다음 가능성을 우선 조사해야 한다.

1. RTNL 락 경합 또는 장시간 점유
2. WSL2 커널 네트워크 처리 정체
3. 가상 네트워크 인터페이스 또는 관련 드라이버 문제
4. 특정 네트워크 변경 작업이 완료되지 않은 상태

단, 현재 출력만으로 RTNL 락의 실제 점유자나 최초 원인을 확정할 수 없다.

# 3. 네트워크 조회 명령어 장애

## 3.1 라우팅 경로 조회

```bash
timeout 5 ip -4 route get 10.244.201.165
echo "route_exit=$?"
```

목적:

WSL에서 FRS 서버까지 어떤 인터페이스와 게이트웨이를 사용하는지 확인.

정상 예시:

```text
10.244.201.165 via 10.x.x.1 dev eth0 src 10.x.x.x
route_exit=0
```

비정상 증상:

- 출력 없이 무한 대기
- timeout 5 이후에도 종료되지 않음

## 3.2 전체 라우팅 테이블 조회

```bash
timeout 5 ip -4 route show
echo "route_table_exit=$?"
```

목적:

- 기본 게이트웨이 확인
- 네트워크 인터페이스별 라우팅 경로 확인

비정상 증상:

- 명령어가 종료되지 않음
- 라우팅 테이블 조회 불가능

## 3.3 /proc/net/route 조회

```bash
timeout 5 cat /proc/net/route
echo "proc_route_exit=$?"
```

목적:

ip 명령어를 사용하지 않고 커널 라우팅 정보를 확인.

확인 사항:

- Destination이 00000000인 행 존재 여부
- 해당 행의 Gateway 값
- 라우팅 인터페이스

주의:

Gateway 값은 일반적인 IP 주소 표기가 아닌 16진수 리틀 엔디언 형식이다.

현재 결과가 확보되지 않았으므로 정상 여부는 미확정이다.

## 3.4 네트워크 인터페이스 조회

```bash
timeout 5 ip -br link
echo "link_exit=$?"
```

목적:

- eth0 등 네트워크 인터페이스 존재 여부
- 인터페이스 UP/DOWN 상태 확인

현재 문제:

ip 명령어가 커널 네트워크 조회 과정에서 멈춰 정상적인 확인이 어려움.

## 3.5 timeout이 작동하지 않는 이유

timeout 명령어는 제한 시간이 지나면 대상 프로세스에 종료 신호를 전달한다.

그러나 대상 프로세스가 D 상태로 커널 내부에서 대기하면 종료 신호가 즉시 처리되지 않을 수 있다.

따라서 timeout이 종료되지 않는 현상은 현재 관찰된 D 상태와 일치한다.

# 4. ARP 및 MAC 주소 확인

실행 명령어:

```bash
arp -a
```

관찰 사항:

WSL에서 Wi-Fi 망의 MAC 주소를 정상적으로 확인하지 못하는 것으로 보고됨.

다만 다음 사항을 구분해야 한다.

### ARP 테이블의 역할

ARP 테이블은 IPv4 주소에 대응하는 링크 계층 MAC 주소를 저장한다.

ARP 테이블에 특정 장비의 MAC 주소가 없다고 해서 해당 네트워크 인터페이스가 존재하지 않는 것은 아니다.

### WSL2 특성

WSL2는 일반적으로 Windows 호스트와 별도의 가상 네트워크 환경을 사용한다.

NAT 또는 mirrored networking 등 WSL 네트워크 모드에 따라 인터페이스 및 ARP 조회 결과가 달라질 수 있다.

따라서 WSL에서 물리 Wi-Fi AP 또는 MOXA의 MAC 주소가 보이지 않는 현상만으로 장애를 확정해서는 안 된다.

확인할 사항:

1. Windows의 ARP 테이블
2. Windows의 Wi-Fi 연결 상태
3. WSL 네트워크 모드
4. WSL 가상 인터페이스 상태
5. FRS 서버까지의 실제 통신 가능 여부

# 5. 원인 분석

## 원인 가설 1. WSL2 RTNETLINK 처리 정체

우선순위: 매우 높음

근거:

- ip 명령어 다수 D 상태
- rtnl_dumpit에서 대기
- rtnetlink_rcv_msg에서 대기
- timeout 이후에도 종료되지 않음
- 기본 Linux 명령어는 정상

가능한 상황:

특정 커널 네트워크 작업이 장시간 완료되지 않으면서 다른 네트워크 조회 요청까지 누적되었을 가능성.

추가 확인 필요:

- 커널 로그
- blocked task 메시지
- RTNL 락 점유 상태
- WSL 커널 버전
- 장애 발생 직전 네트워크 변경 이력

## 원인 가설 2. Windows와 WSL2 가상 네트워크 문제

우선순위: 높음

가능한 원인:

- WSL 가상 네트워크 인터페이스 이상
- Windows Wi-Fi 연결 변경
- VPN 또는 보안 프로그램의 네트워크 필터 영향
- WSL 네트워크 모드와 실제 네트워크 환경의 충돌
- Windows 가상 네트워크 구성 문제

확인 필요:

Windows에서는 FRS 통신이 정상인지 확인해야 한다.

Windows 통신은 정상인데 WSL 통신만 실패한다면 WSL 내부 문제로 장애 범위를 좁힐 수 있다.

## 원인 가설 3. WSL에서 FRS까지 라우팅 문제

우선순위: 중간

FRS 서버:

```text
10.244.201.165
```

Zenoh 확인 포트:

```text
7447
```

가능한 원인:

- 기본 게이트웨이 누락
- 잘못된 정적 라우트
- 네트워크 대역 불일치
- Windows와 WSL의 라우팅 차이
- 사내 네트워크 접근 정책

단, 현재는 ip route 명령어 자체가 멈추기 때문에 실제 라우팅 테이블을 확인하기 전까지 확정할 수 없다.

## 원인 가설 4. Muscat 또는 Zenoh 연결 문제

우선순위: 중간

가능한 원인:

- Zenoh 프로세스 미실행
- Muscat 프로세스 미실행
- 연결 대상 IP 또는 포트 오류
- Zenoh 설정 오류
- Muscat 내부 연결 오류
- FMS와 Muscat 간 애플리케이션 통신 오류

주의:

WSL 네트워크 장애가 Muscat-FMS 통신 실패의 직접 원인인지 아직 확인되지 않았다.

로컬 서비스 상태와 실제 외부 통신을 각각 검사해야 한다.

## 원인 가설 5. MOXA / Wi-Fi / 게이트웨이 문제

우선순위: 추가 확인

확인 사항:

- MOXA가 연결된 SSID
- Windows Wi-Fi IP
- 서브넷 마스크
- 기본 게이트웨이
- MOXA Client/AP 모드
- 공정 4호기와 현재 로봇 PC의 네트워크 설정 차이

MOXA 관리 IP와 기본 게이트웨이 IP는 반드시 동일한 것은 아니다.

초기화 또는 네트워크 설정 변경 전 기존 설정을 확보해야 한다.

# 6. 다음 진단 순서

## STEP 1. Windows 자체 네트워크 확인

실행 위치:

Windows PowerShell

```powershell
Get-NetAdapter |
    Format-Table Name,Status,LinkSpeed,InterfaceDescription

Get-NetIPConfiguration |
    Format-List InterfaceAlias,IPv4Address,IPv4DefaultGateway

route print -4

arp -a
```

확인 목적:

1. Windows Wi-Fi 연결 상태
2. Windows IP 주소
3. Windows 기본 게이트웨이
4. FRS 서버까지의 라우팅 경로
5. Windows ARP 테이블

### FRS TCP 통신 확인

```powershell
Test-NetConnection 10.244.201.165 -Port 7447 -InformationLevel Detailed
```

결과 판단:

TcpTestSucceeded : True

- Windows에서 해당 IP 및 TCP 포트까지 연결 가능

TcpTestSucceeded : False

- TCP 연결 실패
- 라우팅, 방화벽, 서버 리스닝 상태 등을 추가 확인

주의:

TCP 연결 성공은 Zenoh 애플리케이션의 정상 동작까지 보장하지 않는다.

---

## STEP 2. 로컬 Zenoh 확인

실행 위치:

로봇 Windows PC의 PowerShell

```powershell
Test-NetConnection 127.0.0.1 -Port 7447
```

목적:

Windows 루프백 주소의 TCP 7447 포트에서 서비스가 연결을 수락하는지 확인.

판단:

True:

- 로컬 TCP 7447 포트 연결 가능

False:

- 해당 주소와 포트에 연결 불가
- Zenoh 실행 여부 및 리스닝 주소 확인 필요

주의:

127.0.0.1은 명령어를 실행한 환경의 루프백 주소다.

WSL 내부 서비스가 Windows localhost로 노출되는 방식은 WSL 네트워크 모드 및 설정에 따라 다르다.

또한 TCP 7447이 열려 있어도 실제 Zenoh 프로토콜 통신 성공을 보장하지 않는다.

---

## STEP 3. 로컬 Muscat 확인

실행 위치:

Windows PowerShell

```powershell
curl.exe -i --max-time 5 http://localhost:3000/common/docs
```

목적:

Muscat의 HTTP 서비스 접근 여부 확인.

판단:

HTTP 200:

- 해당 엔드포인트 정상 응답

HTTP 401 / 403:

- 서비스 응답은 존재하지만 인증 또는 권한 문제 가능

HTTP 404:

- HTTP 서버는 응답하지만 경로가 없을 가능성

Connection refused:

- 해당 주소 및 포트에서 연결을 수락하지 않음

Timeout:

- 서비스 또는 네트워크 경로 지연 가능성

주의:

문서 페이지가 열리는 것과 Muscat-FMS 통신이 정상인 것은 별개의 문제다.

## STEP 4. WSL 버전 및 설정 확인

실행 위치:

Windows PowerShell

```powershell
wsl --version
wsl --status
wsl --list --verbose
```

확인 사항:

- WSL 버전
- WSL 커널 버전
- Ubuntu 배포판 버전
- WSL1 / WSL2 여부
- 실행 상태

### WSL 설정 파일 확인

```powershell
Get-Content "$env:USERPROFILE\.wslconfig" -ErrorAction SilentlyContinue
```

확인할 설정:

```ini
[wsl2]
networkingMode=nat
```

또는

```ini
[wsl2]
networkingMode=mirrored
```

위 설정은 예시이며 실제 파일에 존재하지 않을 수 있다.

설정 파일이 없다고 해서 반드시 네트워크 장애를 의미하지는 않는다.

현재 단계에서는 수정하지 않는다.

## STEP 6. WSL 프로세스 상태 확보

```bash
ps -eo pid,ppid,stat,wchan:25,comm |
grep -E 'ip|timeout|STAT'
```

D 상태 프로세스 개수 확인:

```bash
ps -eo stat=,comm= |
awk '$1 ~ /^D/ && $2 == "ip" {count++} END {print count+0}'
```

목적:

- D 상태 ip 프로세스 누적 여부
- 장애 지속 여부
- 재시작 전후 비교 자료 확보

추가로 커널 스택 조회를 시도할 수 있다.

```bash
sudo cat /proc/<PID>/stack
```

단, 실제 PID를 사용해야 하며 해당 프로세스가 종료되었을 수 있다.

기존 진단에서는 /proc/PID/stack 조회 자체가 멈추는 현상이 확인되었다.

따라서 반복적으로 실행하지 않는다.

# 8. 해결 방안

## 8.1 1차 조치: 재시작 전 증거 확보

우선 수행:

1. Windows IP 및 게이트웨이 확인
2. Windows → FRS TCP 연결 확인
3. Windows 로컬 Zenoh 포트 확인
4. Windows 로컬 Muscat HTTP 확인
5. WSL 버전 및 네트워크 모드 확인
6. WSL 커널 로그 저장
7. D 상태 프로세스 현황 저장
8. 장애 발생 시간과 직전 변경 사항 기록

현재 단계에서는 아래 작업을 진행하지 않는다.

- MOXA 공장 초기화
- Wi-Fi 설정 변경
- IP 및 게이트웨이 임의 변경
- Windows 네트워크 어댑터 비활성화
- WSL 강제 종료
- Windows PC 재부팅

## 8.2 2차 조치: WSL 재시작

로그 확보 및 서비스 영향 확인 후 진행.

주의:

WSL 내부에서 실행 중인 Muscat, Zenoh 및 관련 서비스가 종료될 수 있다.

실행 위치:

Windows PowerShell

```powershell
wsl --shutdown
```

이후:

```powershell
wsl -d Ubuntu-22.04
```

재시작 후 확인:

```bash
ip -br addr
ip -4 route
ip -4 route get 10.244.201.165
```

정상 출력 여부 확인.

WSL 재시작으로 문제가 사라진다면 일시적인 커널 또는 가상 네트워크 상태 정체 가능성이 높아진다.

단, 재시작만으로 최초 원인이 확정되는 것은 아니다.

## 8.3 3차 조치: Windows / WSL 네트워크 구성 점검

WSL 재시작 후에도 문제가 재발하면 다음을 조사한다.

- WSL 커널 버전 및 업데이트 이력
- Windows 업데이트 이력
- 네트워크 어댑터 드라이버
- VPN 및 보안 프로그램
- WSL NAT / mirrored 네트워크 모드
- 가상 네트워크 어댑터 구성
- Wi-Fi 연결 변경 시점
- 장애 발생 직전 네트워크 설정 변경 여부

WSL 네트워크 모드 변경은 기존 서비스 통신 방식에 영향을 줄 수 있으므로 별도 검증 후 진행한다.

## 8.4 4차 조치: Muscat / Zenoh 설정 확인

WSL 네트워크가 정상화된 이후 확인한다.

- Muscat 실행 상태
- Zenoh 실행 상태
- TCP 7447 리스닝 여부
- 연결 대상 IP 및 포트
- Zenoh connect/listen 설정
- Muscat 로그
- FMS 연결 로그
- FRS 연결 로그

중요:

로컬 포트가 열려 있는 것만으로 실제 FMS와의 애플리케이션 통신 성공을 보장하지 않는다.

실제 연결 로그와 메시지 송수신 여부까지 확인해야 한다.

# 11. 최종 판단 (현재 기준)

## 확인된 사실

1. SI-FMS 통신은 정상으로 보고됨.
2. Muscat-FMS 통신은 실패하고 있음.
3. Windows PC 내부 WSL2 Ubuntu에서 네트워크 조회 명령어가 멈춤.
4. 다수의 ip 프로세스가 D 상태로 확인됨.
5. rtnl_dumpit, rtnetlink_rcv_msg에서 대기하는 프로세스가 존재함.
6. timeout으로도 해당 ip 프로세스가 즉시 종료되지 않음.
7. echo, date 등 기본 명령어는 정상 실행됨.
8. 커널 스택 조회 명령어도 응답하지 않는 현상이 관찰됨.

## 가장 유력한 장애 가설

WSL2 Linux 커널의 RTNETLINK 네트워크 처리 경로에서 장시간 대기 또는 정체가 발생한 상태.

## 아직 확인되지 않은 사항

- RTNL 락의 실제 점유자
- 최초 장애 발생 원인
- Windows → FRS 통신 정상 여부
- WSL의 실제 IP 및 게이트웨이
- Muscat-FMS 통신 실패와 WSL 장애의 직접적인 인과관계
- MOXA 및 Wi-Fi 설정의 영향

## 권장 조치 순서

1. Windows 네트워크 및 FRS 통신 확인
2. 로컬 Zenoh 및 Muscat 상태 확인
3. WSL 커널 로그와 장애 증거 확보
4. 공정 4호기와 네트워크 설정 비교
5. 서비스 영향 확인 후 WSL 재시작
6. WSL 네트워크 조회 및 FRS 연결 재검증
7. Muscat-Zenoh-FMS 통신 복구 확인
8. 재발 시 WSL 커널, 가상 네트워크, 드라이버 및 네트워크 변경 이력 조사
