# [삼성전자 메탈 A동] 공정3호기 FRS 재연결 실패 원인 분석 및 해결 방안

- 작성일: 2026-10-15
- 장애 발생일: 2026-10-04, 2026-10-14
- 대상 장비: 공정3호기 (SEC_Process_2)
- 환경: Windows / WSL2 Ubuntu 22.04 / Muscat / Zenoh / FRS
- 장애 상태: 원인 분석 중
- 조치 원칙: 커널 로그 확보 → 원인 분석 → 서비스 영향 확인 → 복구 및 재발 방지

---

# 1. 장애 요약

## 1.1 문제 상황

공정3호기에서 Windows Wi-Fi 어댑터가 리셋된 이후 WSL2 내부 네트워크 통신이 복구되지 않아 Muscat과 FRS 간 연결이 장시간 끊기는 현상이 발생했다.

일반적으로 Wi-Fi 리셋 후 수십 초 내 FRS에 자동 재연결되지만, 특정 상황에서는 WSL2의 네트워크 처리 경로가 멈추면서 재연결에 실패한다.

### 주요 증상

- SI-FMS 통신 정상
- Muscat-FMS 통신 실패
- Windows → FRS TCP 연결 정상
- WSL → FRS TCP 연결 실패
- WSL `ip route`, `ip addr` 명령어 무한 대기
- 다수의 `ip` 프로세스 D 상태
- Zenoh Bridge 종료 프로세스 확인
- Muscat 연결 상태 `DISCONNECT`
- WSL 내부 FRS 재연결 실패 지속

## 1.2 핵심 판단

**현재 가장 유력한 원인은 Windows Wi-Fi 리셋 과정에서 WSL2 mirrored 네트워크의 커널 처리 경로가 정체되는 현상이다.**

다만 RTNL 락의 실제 점유자와 최초 정체 지점은 확인되지 않았으므로, WSL 커널 버그로 확정하기 위해서는 추가 스택 분석이 필요하다.

# 4. 현장 진단 결과

## 4.1 Windows → FRS 통신

실행 명령어:

```powershell
Test-NetConnection 10.244.201.165 -Port 7447 -InformationLevel Detailed
```

결과:

```text
InterfaceAlias         : Wi-Fi
SourceAddress          : 10.249.138.60
NetRoute (NextHop)      : 10.249.138.1
TcpTestSucceeded        : True
```

### 판단

Windows에서 FRS까지 TCP 연결은 정상이다.

따라서 현재 장애는 Windows의 외부 TCP 경로 전체가 끊긴 상황은 아니다.

## 4.2 WSL → FRS 통신

실행 명령어:

```bash
timeout -k 2s 5s bash -c \
'echo > /dev/tcp/10.244.201.165/7447'

echo "tcp_exit=$?"
```

결과:

```text
bash: connect: No route to host
tcp_exit=1
```

### 판단

WSL에서 FRS까지 TCP 연결이 실패한다.

Windows에서는 동일한 목적지로 연결이 성공하므로 Windows와 WSL 사이의 네트워크 처리 차이가 확인된다.

## 4.3 WSL 라우팅 테이블

실행 명령어:

```bash
cat /proc/net/route
```

확인 결과:

| 인터페이스 | Gateway | Metric |
|---|---|---|
| eth2 | 10.249.138.1 | 60 |
| eth0 | 10.108.2.1 | 281 |
| eth1 | 192.168.0.1 | 291 |

### 판단

WSL의 기본 라우팅 경로는 존재한다.

가장 우선순위가 높은 기본 경로는 Wi-Fi에 대응하는 eth2이다.

따라서 단순한 기본 게이트웨이 누락 문제는 아니다.

## 4.4 ARP 확인

WSL:

```text
10.249.138.1 at <incomplete> on eth2
```

Windows:

```text
10.249.138.1 at 4c-ae-a3-88-be-01
```

### 판단

Windows에서는 Wi-Fi 게이트웨이 MAC 주소가 확인된다.

반면 WSL eth2에서는 ARP가 incomplete 상태다.

이는 WSL 측 이웃 주소 확인이 완료되지 않았다는 의미다.

다만 mirrored 모드에서는 Windows와 WSL의 ARP 표현 및 처리 방식이 다를 수 있으므로, 이 결과만으로 ARP 장애를 확정할 수 없다.

추가로 확보된 eth2 송신 drop 21,569건은 네트워크 이상을 조사할 단서이지만, 누적 카운터이므로 장애 시점의 증가량을 확인해야 한다.

# 5. WSL 커널 장애 분석

## 5.1 ip 명령어 무한 대기

문제 명령어:

```bash
ip addr
ip route
ip -4 route
ip -br link
```

관찰 결과:

- 명령어가 종료되지 않음
- `timeout`으로도 종료되지 않음
- 다수의 `ip` 프로세스가 D 상태
- 커널 함수에서 대기

주요 WCHAN:

```text
rtnl_dumpit
rtnetlink_rcv_msg
```

## 5.2 RTNETLINK란?

RTNETLINK는 Linux 사용자 공간과 커널 사이에서 네트워크 설정 및 상태 정보를 교환하는 인터페이스다.

주요 기능:

- IP 주소 조회
- 네트워크 인터페이스 조회
- 라우팅 테이블 조회
- 네트워크 설정 변경

`ip` 명령어는 RTNETLINK를 사용한다.

현재 RTNETLINK 요청을 처리하는 커널 경로에서 다수의 프로세스가 대기하고 있다.

## 5.3 D 상태의 의미

D 상태는 인터럽트 불가능한 커널 대기 상태다.

이 상태에서는 종료 신호가 즉시 처리되지 않을 수 있다.

따라서 다음 명령어도 정상적으로 종료되지 않을 수 있다.

```bash
timeout 5 ip route
```

### 판단

단순한 TCP 연결 실패를 넘어 WSL 커널의 네트워크 처리 경로에 정체가 발생한 것으로 판단된다.

RTNL 락의 장시간 점유 또는 관련 커널 작업의 정체가 의심된다.

다만 락을 실제로 점유한 프로세스는 아직 확인되지 않았다.

# 6. Muscat / Zenoh 상태

## 6.1 Zenoh Bridge

확인 결과:

```text
[zenoh-bridge-ro] <defunct>
```

### 판단

해당 프로세스는 이미 종료된 좀비 프로세스다.

정상 실행 중인 Zenoh Bridge가 아니다.

단, 다른 Zenoh 프로세스 또는 Docker 컨테이너 내부의 서비스 실행 여부는 별도로 확인해야 한다.

## 6.2 Muscat

확인된 프로세스:

```text
muscat-monitoring/docker-monitor.sh
muscat-version-observer.sh
docker events ...
```

상태 광고:

```text
state=DISCONNECT
```

Windows HTTP 검사:

```powershell
curl.exe -i --max-time 5 http://localhost:3000/common/docs
```

결과:

```text
Failed to connect to localhost port 3000
```

### 판단

Muscat 모니터링 스크립트는 실행 중이나 Muscat 본체의 정상 실행 여부는 확인되지 않았다.

Windows localhost에서 HTTP 서비스 접근이 실패한다.

Muscat이 실행되지 않은 것인지, WSL 내부 바인딩 또는 포트 노출 문제인지 구분해야 한다.

## 8.3 가장 유력한 원인 가설

Windows Wi-Fi 어댑터 리셋을 WSL mirrored 네트워크가 반영하는 과정에서 커널 네트워크 처리 작업이 정체되었을 가능성.

## 8.4 아직 미확정인 사항

- RTNL 락 실제 점유자
- 최초 커널 대기 함수
- Windows Wi-Fi 리셋과 RTNL 고착의 직접 인과관계
- Docker 네트워크의 영향
- Muscat 및 Zenoh 서비스 장애의 선후관계
- NAT 전환 시 재발 방지 효과

# 9. 해결 방안

## 9.1 1차: 커널 로그 확보

현재 장애 상태를 보존한 상태에서 커널 로그를 확보한다.

```bash
sudo dmesg -T > ~/wsl-kernel-dmesg.txt
```

추가로 blocked task 덤프를 검토한다.

```bash
sudo sh -c 'echo w > /proc/sysrq-trigger'
```

주의:

- 관리자 권한 필요
- SysRq 지원 여부 확인 필요
- 커널 로그에 대량 출력 가능
- 장애 중인 WSL에서 명령어 자체가 멈출 수 있음
- 운영 서비스 영향과 로그 수집 경로를 확인한 후 실행

## 9.2 2차: 커널 스택 분석

### 유형 A: Hyper-V / 가상 네트워크 관련

스택에서 다음 함수가 관찰되는 경우:

```text
netvsc
rndis
vmbus
hv_
```

우선 조사:

- WSL mirrored 네트워크
- Hyper-V 가상 네트워크
- Windows Wi-Fi 리셋 이벤트
- Windows와 WSL 간 네트워크 변경 동기화

단, 함수명이 보이는 것만으로 WSL 버그가 확정되는 것은 아니다.

### 유형 B: Docker 네트워크 관련

다음 함수가 관찰되는 경우:

```text
veth
br_
nf_
```

우선 조사:

- Docker 브리지
- veth 인터페이스
- 네트워크 네임스페이스
- netfilter
- 컨테이너 네트워크 재구성

NAT 모드 변경만으로 해결되지 않을 가능성이 있다.

### 유형 C: 락 점유자 확인 불가

blocked task 덤프에서 원인을 찾지 못하면 전체 작업 스택 덤프를 검토한다.

```bash
sudo sh -c 'echo t > /proc/sysrq-trigger'
```

주의:

전체 작업 스택 덤프는 로그량이 매우 클 수 있다.

로그 수집 방법과 저장 공간을 확보한 뒤 수행한다.

## STEP 3. WSL 종료 전 영향 확인

확인 사항:


증상:

단, 이것만으로 WSL에 IP 주소나 게이트웨이가 없다고 단정할 수는 없다.

## 2.1 Linux 기본 명령어 정상

- 네트워크 관련 커널 작업에서 문제가 발생할 가능성이 높음

## 2.2 ip 프로세스 상태 확인

실행 명령어:

```bash
ps -eo pid,ppid,stat,wchan:25,comm | grep -E 'timeout|ip|STAT'
```

주요 결과:

```text
PID     PPID    STAT    WCHAN                 COMMAND

30341   314     D       rtnl_dumpit           ip
237456  237329  D+      rtnetlink_rcv_msg      ip
242289  242274  D+      rtnl_dumpit           ip
246096  246080  S+      sigsuspend            timeout
246097  246096  D+      rtnetlink_rcv_msg      ip
246618  246617  D+      rtnetlink_rcv_msg      ip
246989  246988  D+      rtnl_dumpit           ip
304620  304619  D       rtnl_dumpit           ip
```

실제 출력에서는 이외에도 다수의 ip 프로세스가 D 상태로 확인됨.

### STAT 의미

| 상태 | 의미 |
|---|---|
| R | 실행 중 |
| S | 인터럽트 가능한 대기 |
| D | 인터럽트 불가능한 커널 대기 |
| T | 중지 |
| Z | 좀비 프로세스 |

### WCHAN 의미

rtnl_dumpit

- 커널의 네트워크 정보 조회 처리와 관련된 함수
- 네트워크 인터페이스 또는 라우팅 정보 조회 중 대기하는 상황에서 나타날 수 있음

rtnetlink_rcv_msg

- 커널이 RTNETLINK 요청을 처리하는 경로
- 네트워크 정보 조회 또는 설정 요청 처리 중 정체되었을 가능성

### 판단

다수의 ip 프로세스가 RTNETLINK 관련 커널 함수에서 D 상태로 대기하고 있다.

따라서 단순한 게이트웨이 미설정보다는 다음 가능성을 우선 조사해야 한다.

1. RTNL 락 경합 또는 장시간 점유
2. WSL2 커널 네트워크 처리 정체
3. 가상 네트워크 인터페이스 또는 관련 드라이버 문제
4. 특정 네트워크 변경 작업이 완료되지 않은 상태

단, 현재 출력만으로 RTNL 락의 실제 점유자나 최초 원인을 확정할 수 없다.

# 3. 네트워크 조회 명령어 장애

## 3.1 라우팅 경로 조회

```bash
timeout 5 ip -4 route get 10.244.201.165
echo "route_exit=$?"
```

목적:

WSL에서 FRS 서버까지 어떤 인터페이스와 게이트웨이를 사용하는지 확인.

정상 예시:

```text
10.244.201.165 via 10.x.x.1 dev eth0 src 10.x.x.x
route_exit=0
```

비정상 증상:

- 출력 없이 무한 대기
- timeout 5 이후에도 종료되지 않음

## 3.2 전체 라우팅 테이블 조회

```bash
timeout 5 ip -4 route show
echo "route_table_exit=$?"
```

목적:

- 기본 게이트웨이 확인
- 네트워크 인터페이스별 라우팅 경로 확인

비정상 증상:

- 명령어가 종료되지 않음
- 라우팅 테이블 조회 불가능

## 3.3 /proc/net/route 조회

```bash
timeout 5 cat /proc/net/route
echo "proc_route_exit=$?"
```

목적:

ip 명령어를 사용하지 않고 커널 라우팅 정보를 확인.

확인 사항:

- Destination이 00000000인 행 존재 여부
- 해당 행의 Gateway 값
- 라우팅 인터페이스

주의:

Gateway 값은 일반적인 IP 주소 표기가 아닌 16진수 리틀 엔디언 형식이다.

현재 결과가 확보되지 않았으므로 정상 여부는 미확정이다.

## 3.4 네트워크 인터페이스 조회

```bash
timeout 5 ip -br link
echo "link_exit=$?"
```

목적:

- eth0 등 네트워크 인터페이스 존재 여부
- 인터페이스 UP/DOWN 상태 확인

현재 문제:

ip 명령어가 커널 네트워크 조회 과정에서 멈춰 정상적인 확인이 어려움.

## 3.5 timeout이 작동하지 않는 이유

timeout 명령어는 제한 시간이 지나면 대상 프로세스에 종료 신호를 전달한다.

그러나 대상 프로세스가 D 상태로 커널 내부에서 대기하면 종료 신호가 즉시 처리되지 않을 수 있다.

따라서 timeout이 종료되지 않는 현상은 현재 관찰된 D 상태와 일치한다.

# 4. ARP 및 MAC 주소 확인

실행 명령어:

```bash
arp -a
```

관찰 사항:

WSL에서 Wi-Fi 망의 MAC 주소를 정상적으로 확인하지 못하는 것으로 보고됨.

다만 다음 사항을 구분해야 한다.

### ARP 테이블의 역할

ARP 테이블은 IPv4 주소에 대응하는 링크 계층 MAC 주소를 저장한다.

ARP 테이블에 특정 장비의 MAC 주소가 없다고 해서 해당 네트워크 인터페이스가 존재하지 않는 것은 아니다.

### WSL2 특성

WSL2는 일반적으로 Windows 호스트와 별도의 가상 네트워크 환경을 사용한다.

NAT 또는 mirrored networking 등 WSL 네트워크 모드에 따라 인터페이스 및 ARP 조회 결과가 달라질 수 있다.

따라서 WSL에서 물리 Wi-Fi AP 또는 MOXA의 MAC 주소가 보이지 않는 현상만으로 장애를 확정해서는 안 된다.

확인할 사항:

1. Windows의 ARP 테이블
2. Windows의 Wi-Fi 연결 상태
3. WSL 네트워크 모드
4. WSL 가상 인터페이스 상태
5. FRS 서버까지의 실제 통신 가능 여부

# 5. 원인 분석

## 원인 가설 1. WSL2 RTNETLINK 처리 정체

우선순위: 매우 높음

근거:

- ip 명령어 다수 D 상태
- rtnl_dumpit에서 대기
- rtnetlink_rcv_msg에서 대기
- timeout 이후에도 종료되지 않음

가능한 상황:

추가 확인 필요:

- 커널 로그
- blocked task 메시지
- RTNL 락 점유 상태
- WSL 커널 버전
- 장애 발생 직전 네트워크 변경 이력

## 원인 가설 2. Windows와 WSL2 가상 네트워크 문제

우선순위: 높음

가능한 원인:

- WSL 가상 네트워크 인터페이스 이상
- Windows Wi-Fi 연결 변경
- VPN 또는 보안 프로그램의 네트워크 필터 영향
- WSL 네트워크 모드와 실제 네트워크 환경의 충돌
- Windows 가상 네트워크 구성 문제

확인 필요:

Windows에서는 FRS 통신이 정상인지 확인해야 한다.

Windows 통신은 정상인데 WSL 통신만 실패한다면 WSL 내부 문제로 장애 범위를 좁힐 수 있다.

## 원인 가설 3. WSL에서 FRS까지 라우팅 문제

우선순위: 중간

FRS 서버:

```text
10.244.201.165
```

Zenoh 확인 포트:

```text
7447
```

가능한 원인:

- 기본 게이트웨이 누락
- 잘못된 정적 라우트
- 네트워크 대역 불일치
- Windows와 WSL의 라우팅 차이
- 사내 네트워크 접근 정책

단, 현재는 ip route 명령어 자체가 멈추기 때문에 실제 라우팅 테이블을 확인하기 전까지 확정할 수 없다.

## 원인 가설 4. Muscat 또는 Zenoh 연결 문제

우선순위: 중간

가능한 원인:

- Zenoh 프로세스 미실행
- Muscat 프로세스 미실행
- 연결 대상 IP 또는 포트 오류
- Zenoh 설정 오류
- Muscat 내부 연결 오류
- FMS와 Muscat 간 애플리케이션 통신 오류

주의:

WSL 네트워크 장애가 Muscat-FMS 통신 실패의 직접 원인인지 아직 확인되지 않았다.

로컬 서비스 상태와 실제 외부 통신을 각각 검사해야 한다.

## 원인 가설 5. MOXA / Wi-Fi / 게이트웨이 문제

우선순위: 추가 확인

확인 사항:

- MOXA가 연결된 SSID
- Windows Wi-Fi IP
- 서브넷 마스크
- 기본 게이트웨이
- MOXA Client/AP 모드
- 공정 4호기와 현재 로봇 PC의 네트워크 설정 차이

MOXA 관리 IP와 기본 게이트웨이 IP는 반드시 동일한 것은 아니다.

초기화 또는 네트워크 설정 변경 전 기존 설정을 확보해야 한다.
